# Архітектура

## Шари

```
feature (Compose UI + ViewModel)  →  domain (моделі, логіка, інтерфейси репозиторіїв)  ←  data (Room, DataStore, файли)
```

- **domain** не залежить від Android. Уся «розумна» логіка — чисті функції з JVM-тестами:
  `ScheduleCalculator` (ротація, пропуски, серія), `WorkoutFlow` (що показати зараз),
  `ProgressMath` (e1RM, рекорди), `ProgressionAdvisor`, `StatsCalculator`.
- **data** реалізує репозиторії. Лише `RepositoryModule` знає, яка реалізація за інтерфейсом —
  саме туди підключиться синхронізація з хмарою.
- **feature** — екран = `Screen` (Compose) + `ViewModel` зі `StateFlow<UiState>`.

Один Gradle-модуль, поділ за пакетами. Багатомодульна збірка (як у Now in Android) виправдана для
команди або при довгих збірках; для одного розробника вона додає конфігурації без реальної вигоди.
Межі пакетів уже відповідають майбутнім модулям (`domain`, `core:database`, `feature:*`), тож
розділити можна механічно, коли знадобиться.

## Ключові рішення

**Ротація A → B → C замість «понеділок = A».** Наступне тренування — те, що йде після останнього
виконаного. При фіксованій привʼязці пропуск середи означав би A, C, A… і B не робилося б ніколи.

**Стан активного тренування живе в базі.** Сесія створюється при «Почати»; кожен підхід, поточна
вправа і час кінця відпочинку одразу записуються. Екран лише читає й перераховує крок через
`WorkoutFlow`. Тому тренування переживає вбивство процесу, перезавантаження телефона чи випадковий
свайп — на головній буде «Продовжити». Забуте тренування (>3 год без підходів) можна закрити часом
останнього підходу, щоб не зіпсувати статистику тривалості.

**Знімок плану в історії.** Під час старту вправи тренування копіюються в `session_exercise`
(назва, діапазони, вага, відпочинок). Подальше редагування програми не переписує минулі тренування.

**Таймер відпочинку.** Відлік рахується від абсолютного часу кінця (`rest_ends_at`), а не тиками.
Сигнал подають два шляхи, і спрацьовує лише перший (`TimerAlertCoordinator`):
корутина в процесі (точна, поки застосунок відкритий) і `AlarmManager` (працює у фоні та після
вбивства процесу). У застосунку — звук/вібрація, у фоні — сповіщення. Постійне сповіщення показує
відлік системним хронометром — без foreground-сервісу, який Google Play вимагає обґрунтовувати.
Екран під час тренування не гасне (налаштовується).

**Точні будильники.** На Android 14+ дозвіл «Будильники й нагадування» за замовчуванням вимкнений.
Без нього система може затримати сигнал на хвилини. Застосунок падає назад на неточні будильники й
показує в налаштуваннях попередження з кнопкою дозволу. `USE_EXACT_ALARM` не використовується —
Google Play дозволяє його лише будильникам і календарям.

**Серія — у тижнях, не в днях.** Для програми 3×/тиждень денна серія обнулялася б через день.
Тиждень зараховується, якщо виконано не менше тренувань, ніж днів у розкладі; поточний
незавершений тиждень серію не рве.

**Пропущені тренування.** Запланований день без тренування в цю дату. Тренування, перенесене на
інший день, залишає запланований день «пропущеним» — просте й передбачуване правило, яке збігається
з календарем. Рахуються лише дні після першого запуску застосунку.

**Графіки на Canvas, без бібліотеки.** Потрібні лише лінійний і стовпчиковий графіки однієї серії;
API бібліотек графіків часто ламається між версіями. Під кожним графіком — текстовий список значень.

**Українська локаль закріплена.** Інтерфейс лише український, але Android обирає форму множини
(«підхід/підходи/підходів») за мовою системи. Без фіксації на англомовному телефоні було б
«20 підходу». Прибрати, коли зʼявляться інші мови.

## База даних (Room, версія 1)

```
program ──< workout_template ──< template_exercise >── exercise ──< exercise_image
   │               │                                      │
   └──(SET NULL)───┴──< workout_session ──< session_exercise >──┘ (RESTRICT)
                                                  └──< set_log
user_profile (1 рядок)      measurement_type ──< body_measurement
```

| Таблиця | Призначення |
|---|---|
| `program` | програма; одна активна (`is_active`) |
| `workout_template` | тренування програми (A/B/C), `order_index` задає ротацію |
| `template_exercise` | вправа в тренуванні: `sets_min/max`, `reps_min/max`, вага, відпочинок |
| `exercise`, `exercise_image` | бібліотека вправ; фото — імʼя файлу в `files/exercise_images/` |
| `workout_session` | тренування: дата, початок/кінець, статус, поточна вправа, відпочинок |
| `session_exercise` | знімок плану вправи + статус (очікує / виконано / пропущено) |
| `set_log` | підхід: вага (кг), повторення, RPE, відмова, примітка, час |
| `user_profile` | імʼя, дата народження, зріст |
| `measurement_type`, `body_measurement` | параметри тіла та повна історія вимірювань |

- **UUID-ключі** замість автоінкременту: записи з різних пристроїв не конфліктують під час майбутньої
  синхронізації чи злиття бекапів. Синхронізовані таблиці мають `created_at` / `updated_at`.
- Вага завжди в кг; фунти — лише відображення. Час — `Instant` (epoch ms), дати — `LocalDate` (epoch day).
- Вправу з історією видалити не можна (`RESTRICT`) — історія й прогрес не втрачаються.
- Схема експортується в `app/schemas/`: кожна зміна версії повинна мати `Migration`, без
  `fallbackToDestructiveMigration`.
- Налаштування — у DataStore (невеликі, лише для цього пристрою, без запитів).

## Експорт та імпорт (CSV)

- `domain/transfer` — чиста логіка без Android, з JVM-тестами: `Csv` (RFC 4180, BOM, визначення
  роздільника), `Values` (числа з комою, «16(2)», дати різних форматів, тривалість), `ColumnMapping`
  (синоніми заголовків укр./англ., колонки підходів «С1 вага»), `WorkoutFileParser` (рядок на підхід
  або на вправу, контекст «Дата: …» над блоком), `ImportPlanner` (зіставлення вправ і дублікати),
  `BodyImport`, `CsvExport`.
- Файл без дат із колонками «Тренування / Вправа / Підходи / Повторення» — це програма
  (`ProgramFileParser`): створюється нова програма з тренуваннями в порядку файлу (це й ротація).
  Вправи зіставляються так само, як в історії. Скасування видаляє програму й повертає попередню
  активну.
- Дублікати: тренування з тією самою датою й назвою (і часом, якщо відомий) не імпортується. Якщо
  набір підходів збігається — це дублікат; якщо ні — конфлікт: наявне тренування не змінюється, у
  звіті видно, що саме пропущено.
- `DataTransferRepositoryImpl` записує весь план в одній транзакції. Створені id зберігаються в
  `files/transfer_history.json` — «Скасувати імпорт» видаляє рівно їх. Так само обʼєднання вправ
  запамʼятовує, що куди перенесено, і повертає все назад. Схема бази не змінювалась (версія 1),
  тож оновлення застосунку не мігрує й не чіпає наявні дані.
- Імпортовані тренування без часу зберігаються з початком о 00:00 і без тривалості; інтерфейс не
  показує для них «00:00». Вони мають `template_id = NULL`, тож не впливають на ротацію A/B/C, а
  пропуски рахуються лише від першого запуску застосунку.

## Як додати синхронізацію / бекап

1. Для синхронізації додати tombstone-поле `deleted_at` (міграція v2) і фільтр у DAO.
2. Нова реалізація репозиторіїв (локальна БД + віддалений API) підміняється в `RepositoryModule`.
3. Auto Backup уже налаштований (`data_extraction_rules.xml`): база, налаштування й фото потрапляють
   у резервну копію Google та при перенесенні на новий телефон.

## Тести

- `app/src/test/.../domain` — чиста логіка (розклад, крок тренування, прогрес, статистика).
- `app/src/test/.../core` — нагадування та повний шлях таймера відпочинку: будильник →
  receiver → сповіщення, без дублювання.
- `app/src/test/.../domain/transfer` — CSV: розбір, формати чисел і дат, мапінг колонок, журнальні
  блоки, дублікати, синоніми вправ, експорт → імпорт без втрат.
- `app/src/test/.../data` — імпорт у справжню Room-базу: історія, статистика, прогрес, повторний імпорт,
  скасування, обʼєднання вправ; збереження фото (JPEG/PNG/WebP, великі, EXIF, SVG, пошкоджені,
  content:// і file://) на Android 15 (ImageDecoder) та Android 8 (BitmapFactory).
- `app/src/test/.../ui` — сценарії на справжній `MainActivity` під Robolectric: проходження
  тренування, скасування, історія та статистика на 6 тижнях даних, редактор програм, вимірювання,
  налаштування, таймер. Скриншоти — у `app/build/screenshots/`.

Обмеження тестів: Robolectric не рендерить діалоги й нижні панелі в скриншоти (вони перевіряються
через семантику), а `AlertDialog` із текстовим полем під ним ніколи не стає «idle». Тому форми з
полями зроблені нижніми панелями. На реальному пристрої чи емуляторі варто один раз пройти сценарії
вручну: сповіщення, фото з галереї, поведінку з вимкненим екраном.

## Відомі обмеження

- Окремий таймер тримає стан у памʼяті: якщо Android вбʼє процес, сигнал прийде, але екран таймера
  скинеться. (Відпочинок у тренуванні зберігається в базі й відновлюється.)
- Фото додаються з галереї (Photo Picker) або з файлів (Downloads, хмарні диски); зйомки камерою
  безпосередньо із застосунку немає. Файл читається один раз і перекодовується в JPEG ≤ 1600 px;
  прозорий фон PNG/WebP стає білим.
- Імпорт читає CSV; файли .xlsx потрібно зберегти як CSV (застосунок про це підкаже).
